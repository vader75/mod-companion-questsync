# Companion custody: phased rollout and retirement

QuestSync and legacy `mod-wowlegends` share the AddClass account population. A playerbot can also be an ordinary alt. Neither manager control, AddClass account type, a matching name, nor a release timestamp proves current companion ownership. The shared `cq_companion_custody` table is an explicit, audited reservation **per body GUID**. The modules own separate portions of stock (`cq` and `legacy`).

## 1. Deploy both guards before enabling claims

1. While the realm is cleanly stopped, back up the characters database and preserve the old binding and release tables for review. Deploy **both** guarded modules as a pair. Do not run an older module against the shared pool: it does not honor custody. Do not rerun the older destructive compatibility migration.
2. Apply the current additive `sql/companion-questsync.sql` and `sql/companion-custody.sql` to the **characters** database. Legacy installs its canonical `wowlegends_companion` table at startup if missing. Use `cq_bindings` in QuestSync. The old `RespectLegacyBindings` switch cannot bypass exclusions. Require InnoDB and a single-column unique key on `bot_guid` in each binding table; legacy also requires a unique `owner_guid`. The additive SQL does not silently repair bad historical indexes. Review those separately before enabling operations.
3. Start with **empty custody**, not a blind backfill. New claims and verified companion actions are unavailable until seeded. Existing unreviewed binding rows and compatibility bindings still reserve bodies, and unreviewed CQ bindings still count toward the owner's cap. No boot repair or periodic cleanup should turn ambiguous records into stock. Coexisting old `wowlegends_companion_multi` rows block the affected bodies until reconciled offline; release logs (`wowlegends_companion_released`, `cq_pool`, and older ledgers) are for diagnosis only, including same-second ties.

## 2. Review a limited cohort offline

- Keep AddClass accounts dedicated: no ordinary character login, raw `.playerbots` access to free stock, pool regeneration, transfers or external character writers on enrolled GUIDs. Manually reconcile any such use, restore, or GUID reuse before bringing the cohort back online. A GUID plus account/name cannot detect a replacement with all three fields reused.
- **Free:** prefer newly provisioned, never-used level-one bodies. Independently confirm the body is on a dedicated AddClass account, offline, unbound in *all* current/historical binding tables, not guilded/AHBot, and carries no prior owner's gear, mail, quests, group, chat/companion memory or other character-side state. Assign one module. Insert one row with `bot_guid`, `module`, `body_account`, exact `body_name`, `owner_guid = 0`, `state = 'free'`, `tracking = 0`, and a `reviewed_by` reference to the operator/audit evidence. Do not populate stock from account type or historical release records alone.
- **Existing owner:** after independent evidence links the current owner to the current body incarnation, reconcile duplicate/conflicting bindings, confirm body account and exact live name, and insert `state = 'owned'` with the matching **canonical** binding and owner GUID. Set `tracking = 1` for CQ if wanted, otherwise `0`. Leave uncertain rows untouched and reserved. Changing the custody table online, with world caches loaded, is unsupported.
- Both create paths recheck identity, stock, incompatible bindings, `online`, AddClass account, basic level/login/group restrictions and name availability at claim. The character rename, explicit ownership and binding commit together before cache updates/summon. A clean body is never wiped on create. CQ `unbind` only turns off tracking; `bind` resumes tracking on a verified body already owned by that player, even offline. The body and owner slot remain reserved while untracked.

**Heroic stock is unavailable in both allocators.** Do not enroll Death Knights as `free`, even on a realm configured for a level-one heroic start. Level alone cannot verify a clean heroic starting state. Stock counts and claims exclude Death Knights, and a direct create request reports that they are unavailable. Existing independently verified owned Death Knights are unaffected.

QuestSync module hand-ins require the owner's personal playerbot manager and current tracked custody. Bring the companion into native interaction range of a live quest ender; static spawn records can supply directions and pins but never move the companion or permit a reward. Mode `0` opts out of module hand-ins, mode `1` uses native interaction, and mode `2` adds a lead-to-giver reminder when outside `HandInNearDistance`. Neither mode teleports the companion to the giver.

## 3. Retirement is not recycling

- CQ `release` durably changes verified ownership to `retiring` before requesting dismissal, rejects a summon in flight, and stops waiting after 15 seconds without removing the reservation. Legacy `forget`/`destroy yes` require a verified body already dismissed and not loading or initializing, then persist `retiring`. Either request removes the body from normal companion actions, retains the binding and name, and never schedules a reset after a restart.
- The playerbots logout path queues character saves before removing the body. A disconnected object, `online = 0`, a delay, or an unrelated synchronous SQL query are **not** completion barriers for all character DB workers. Do not enable automatic runtime reset without a core save-completion contract covering all relevant writes, login exclusion, and an independently verified full reset path.
- To free an owner slot, first cleanly stop all world processes, confirm DB writers have drained (not a crash or forced termination), back up and reconcile the specific GUID. Optionally install `sql/companion-retirement-maintenance.sql` once, on a validated schema with both canonical binding tables and transactional engines. Then explicitly call `cq_finalize_companion_retirement(module, bot_guid, owner_guid, body_account, exact_name)` for one reviewed `retiring` row. It refuses conflicts or identifier drift and atomically marks the body `retired` and removes **only** the matching binding. It never frees the character name or resets/deletes the character. Inspect/read back `characters`, both binding tables and custody after each call. Preserve retired rows as tombstones; replenish with new verified stock rather than changing `retired` to `free`.
- Game commands, another server process, old module binaries and direct DB/world tools outside these modules are not globally fenced. Do not treat a rollback to old binaries as safe without first disabling all old lifecycle paths and reviewing reserved rows. This phase deliberately sacrifices one-click recycling. In-game behavioral verification remains a separate rollout gate.

## 4. One-time QuestSync starter bags

**Install together, offline.** In a writable source checkout matching the repack archive, run the following **from the `mod-playerbots` root**, not from the core or QuestSync root:

```sh
git -c core.autocrlf=false apply --check /absolute/path/to/patches/mod-playerbots-companion-initialization.patch
git -c core.autocrlf=false apply /absolute/path/to/patches/mod-playerbots-companion-initialization.patch
```

Build Playerbots and QuestSync together as static modules (the tested project layout). Apply `sql/companion-starter-bags.sql` once to the **characters** database after the custody schema and before booting. The migration adds a nullable marker with no backfill. Without the compatible Playerbots API, working registration, or migration, claims still work on the base custody schema but do not arm the grant; those claims are not backfilled when alignment is installed. Unpatched Playerbots keeps its native behavior, so unpatched mode does **not** promise protection from native refills or login reset. A patched, registered build protects custody even when the item migration is not installed or QuestSync is disabled. A competing provider is not a compatible aligned build; registration failure is logged and disables the grant. Don't change schema or roll back the patch/binary on a running world.

- An aligned new claim arms one lifetime attempt. The confirmed summon (or the first upkeep pass that verifies the owner's personal-manager session and exact tracked custody) consumes the marker before touching inventory. Playerbots' bag-only helper attempts only the four equipped bag slots, with no swap, alternate placement, or occupied slot write. Item 51809 is Portable Hole (24 general-purpose slots). All four occupied still spends the attempt; existing items are not replaced. `ExtraBagItem`/`ExtraBags` still control ordinary empty-slot upkeep (default 20400); 51809 is rejected there.
- Consumption is not atomic with the asynchronous core inventory save. A crash, invalid item template, or equip/save failure can leave fewer or no bags; a spent attempt never retries. An unconfirmed DB write does not authorize equip; if no write committed, a later verified pass may attempt it. Require `innodb_flush_log_at_trx_commit=1` on the same primary used for inventory writes. Preserve markers and retirement tombstones through backup/restore; never clear/rearm a marker or combine reverted custody with newer inventory or sales.
- The archive loads module scripts before starting the DB, then runs the world config hook before native Playerbots initialization and the world loop. QuestSync registers a generic Playerbots veto during script load and probes custody metadata in the config hook. The veto queries the **exact body GUID** in the shared custody ledger; it covers `cq/owned` and `cq/retiring` even if untracked or the binding has drifted. Successful negative results leave other bots alone (including other bodies on the same account); ambiguous reads defer initialization rather than risk a reset. With no provider or a confirmed absent custody table, native behavior is unchanged. The starter grant itself additionally requires the matching live session, owner, account/name, canonical binding and no foreign binding.
- Both native issuance paths are fenced centrally: `PlayerbotHolder::OnBotLogin` (AddClass, owner level gap over three) reaches `PlayerbotFactory::Randomize`, vetoed before `Prepare` or any reset; both maintenance branches in `TrainerAction.cpp` reach the vetoed `InitBags(false)`. Factory vetoes also cover manual `init=`, `level`/`levelup`, `random` and random-manager callers that reach `Randomize`; the AddClass command explicitly reports refusal. `Refresh`, `ClearEverything` and `InitInstanceQuests` may still mutate **contents**, not equipped bag slots or issue 51809; other maintenance work remains unchanged. `EquipAction` can swap an already-owned bag as normal gear gameplay; AddClass character creation uses normal `Player::Create`. This is not a global restriction on loot, trade, purchases, player-directed equipment, GM tools or arbitrary SQL.

**Rollout gate:** A disposable world must still verify an empty four-slot first summon, one or more existing bags with contents and stable item GUIDs, unchanged inventories through a later >3-level-gap login and both applicable maintenance branches, no 51809 refill after removal/sale, and normal initialization for a non-QuestSync body. Read back equipped slots 19–22 and item GUIDs after saving/relogin. The patch and SQL fixture do not prove gameplay or worldserver linking.

## Local verification

`python -B -m unittest discover -s tests` runs the QuestSync tests (SQL tests skip by default). The SQL integration suite runs against a **disposable** MySQL fixture with the Windows named pipe `cq_lifecycle_audit_fixture`, `--skip-networking`, initialization in a new scratch data directory and no option files. Set `CQ_TEST_MYSQL` to the isolated fixture's client executable (the test forces the named pipe), and put the legacy worktree adjacent as `../legacy` or set `CQ_TEST_LEGACY`. Run `python -B -m unittest discover -s tests -p test_lifecycle_mysql.py -v`. The tests exercise production claim SQL (including without the optional migration/capability), exact-GUID native reservation, one winning token, partition/foreign-binding rejection, same-second history, untracking, rollback on failed insert and atomic offline retirement. They do not run a worldserver or prove Playerbots thread/session behavior.
